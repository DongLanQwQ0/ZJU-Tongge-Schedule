# 待办与规划

> 这份文档只记**方向和坑**，不是已实现的功能。
> 每一条都写清楚「现在是什么样」，免得日后误以为已经做过了。

---

## 0. 现状盘点（写文档时的真实状态）

先说清楚已经有什么，后面几节的「缺什么」才有参照。

| 方面 | 现在 |
|---|---|
| 传输 | 明文 HTTP，绑定 `0.0.0.0`，校园网内可访问。**密码在网络上裸奔** |
| 密码存储 | scrypt（N=16384, r=8, p=1, keylen=64）+ 16 字节随机盐，`timingSafeEqual` 比对 |
| 会话 | 32 字节随机 token，90 天滑动过期，存 `data/sessions.json` |
| 鉴权载体 | `Authorization: Bearer <token>`，**不用 Cookie** |
| 存储 | 三个 JSON 文件 + `groups/*.json`，原子写（`.tmp` + `rename`），单文件写队列 |
| 请求体 | 上限 1 MB |
| 限流 | 全局 600/分、入群 20/分、注册突发 8/10分、注册 20/时、登录失败 30/10分；另有按昵称的 5 次失败锁 60 秒 |
| 审计 | `data/audit.log`（JSON Lines）：注册、注册被限流、注销、管理员操作 |
| 异常识别 | 同 IP 24 小时内注册 ≥6 个账号则整簇标记 `suspect`，登录页横幅提示 |
| 输入清洗 | 昵称剥控制字符与文件系统保留字符；课表结构逐字段校验；路径映射做了越界检查 |

**两个值得记下的既有优势**（后面别改坏了）：

- 不用 Cookie，改用 Bearer token ⇒ **天然免疫 CSRF**。以后如果为了省事换成 Cookie，必须同时补 SameSite + CSRF token。
- 课表在**浏览器端解析**，只上传结构化 JSON ⇒ 服务端不接触原始 `.ics`，也就没有对应的解析漏洞面。

## 1. 服务端超时与抗打

**现在**：`server.js` 里**一个超时都没设**。默认状态下 Node 允许连接长时间挂着不发完请求头，这正是 Slowloris 这类慢速攻击的着力点。另外没有连接数上限，也没有单 IP 并发上限。

**要做**：

- `server.headersTimeout` / `requestTimeout` / `keepAliveTimeout` 三个都显式设上
- 单 IP 并发连接数上限
- 限流从「按 IP」升级为「按 IP + 按账号」双轨 —— 现在攻击者换 IP 就能绕过
- 检查 `readBody`：超大 body 是在读之前就拒绝，还是读完才拒绝？（应当边读边掐）

**坑**：限流阈值调紧会误伤 —— 同一个教室几十个人连同一个 NAT 出口是很正常的。**宿舍楼、机房、教学楼 WiFi 出口 IP 会重合**，按 IP 封禁要留白名单或短封禁时间的余地。

---

## 2. 定时备份与恢复

**现在**：完全没有备份。`data/` 下的 `users.json` 已经 183 KB，是唯一的真身。

**要做**：

- 定期快照整个 `data/`，保留多代（例如滚动 7 天 + 每周归档）
- 快照要能**离线校验**：存个校验和，不然备份坏了也不知道
- 恢复演练 —— 没实际恢复过一次的备份不算备份

**坑（最容易被忽略的一条）**：**攻击者污染数据后，定时备份会把污染一起存下来。** 单纯「每天备份一次」挡不住「删库跑路后等到第二天」这种情况。所以：

- 保留**写前快照**（每次改 `users.json` 前的上一版），而不只是定时快照
- 保留**足够长的历史代次**，能回溯到污染之前
- 审计日志应当**只追加、不可改**，它是唯一能重建「什么被改过」的证据

---

## 3. 识别并阻止恶意攻击

**现在**：有审计日志、有可疑账号标记、有限流器 —— 但**没有任何自动反应**，也没人盯日志。日志只在服务器启动时把待复核账号打印一遍。

**要做**：

- 管理页里的审计日志加上**聚合视图**：按 IP、按事件类型、按时间分布，而不是现在这样一条条平铺
- 检测信号 → 自动动作：登录失败激增、单 IP 请求速率突增、同一昵称被反复尝试
- 分级反应：先限速、再临时封禁、最后才人工介入
- **封禁要能自动解除**，否则一次误判就等于把一个正常同学永久挡在门外

---

## 4. 课表匹配（找相似课表的人）

**现在**：只能「进群 → 看群里谁和我重合」。没有跨群匹配，没有陌生人匹配。

**要做**：

- 相似度口径：重合课时数？重合比例（Jaccard）？空闲时间是否对得上？
- 匹配结果要说明**依据**，不能只给一个分数（「你们周三下午都在东 6」比「相似度 82%」有用得多）
- 匹配是主动发起的，不是自动推送的

**用户协议与同意**：

- 必须显式同意《用户协议》+《隐私政策》，**不能默认勾选**
- **同意要留痕**：记录同意的**时间**和**协议版本号**，不能只存一个 `agreed: true` —— 协议改版后旧同意是无效的
- 同意要能**撤回**，且撤回后数据要真的断开，不是只把开关关掉
- 要写清楚「我的课表会给谁看」：进群可见？还是匹配到的陌生人也可见？这两者风险完全不同

**坑（这是全项目风险最高的一环）**：现在的可见范围是「同群成员」，本质上是熟人网络 —— 你得先拿到邀请码。**一旦开放陌生人匹配，就从「熟人可见」变成「陌生人可见」**，课表里含真实姓名、每周行踪、常去的楼栋教室。这一条上线前应当单独做一次评审，不要和其他功能混在一个版本里发。

---

## 5. 接入学校身份认证

**现在**：谁都能注册，昵称全局唯一但没有任何真实性保证。邀请码是群组内容的唯一门槛。

**要做**：

- 浙大统一身份认证（CAS / OAuth 那条线）
- 认证通过后绑定账号，用于「这个人确实是本校学生」这一件事

**坑**：

- 引入**外部依赖**：内网服务要能访问外网认证服务器。学校认证挂了怎么办？必须有降级路径，不能让整个站点跟着躺
- **学校认证 ≠ 这个人可信**，只等于「确实是本校学生」。校内同学互相攻击的动机和手段并不更少
- 存储边界要想清楚：学号、姓名这类信息**能不存就不存**，至少要存哈希而不是原文
- 和现有的「昵称 + 密码」体系怎么共存？强制绑定还是可选升级？老账号怎么办？

---

## 6. 传输加密

**现在**：明文 HTTP。密码、会话 token 全程明文过校园网，同一个 WiFi 下抓包可见。这是本设计**最大的短板**，文档里一直明示着。

**要做**：自签证书 + HTTPS，或放到反向代理后面。注意自签证书在手机上的信任问题 —— 学校同学不会为了用这个去装根证书。

**这条应当排在匹配功能之前。** 因为「陌生人之间的隐私风险」只有在传输本身安全的前提下谈才有意义。

---

## 优先级建议

1. **传输加密**（第 6 项）—— 它是其他所有隐私讨论的前提
2. **备份 + 写前快照**（第 2 项）—— 成本最低，救的是最不可逆的损失
3. **超时与限流加固**（第 1 项）—— 小改动，挡掉最省事的攻击
4. **审计聚合与自动封禁**（第 3 项）—— 在有人开始攻击之后再补就晚了
5. **学校身份认证**（第 5 项）—— 收益大但外部依赖重，可以晚
6. **课表匹配**（第 4 项）—— **功能上最有意思，风险上也最重，放最后，且单独评审**

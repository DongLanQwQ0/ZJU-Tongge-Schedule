# 管理页账号筛选与排序 —— 设计

> 一句话：**管理页的账号列表从「一个搜索框」升级成「搜索 + 状态胶囊 + 排序 + 区间筛选」，全在浏览器里算，服务端一行不动。**

## 1. 现状

管理页的「账号」卡片只有一颗输入框 `#admin-user-filter`（`public/index.html:175`），
`renderAdminUsers(q)`（`public/app.js:708`）拿它做一件事：**昵称或注册 IP 的子串匹配**。

排序完全没有——列表顺序就是服务端 `readUsers()` 读出来的文件顺序，也就是**注册先后**。

服务端那边其实**已经把该给的字段全给了**。`store.listAdminUsers()`（`shared/store.js:1628`）
手工挑出 14 个字段：

```
id  nickname  courseCount  regIp  regAt  lastLoginAt  lastLoginIp
loginCount  idleDays  dormant  admin  super  suspect  suspectReason
```

`/api/admin/overview` 一次性把全部账号发给前端，前端手里**已经握着完整数据集**。
所以这是一个纯粹的前端功能——加一个筛选/排序层，不动接口、不动存储、不动鉴权。

## 2. 目标与非目标

**做**：按状态、注册时间、活跃度、课表筛选；按六个字段任选正/倒序排序。

**不做**：

- ❌ 服务端查询参数（`?status=&sort=`）——见 §3
- ❌ 群组列表的筛选（这次只做账号）
- ❌ 保存筛选偏好到 localStorage（进页面一律重置，见 §7.4）
- ❌ 导出筛选结果 / 批量操作（选中多行批量删号是另一个功能，且风险等级完全不同）

## 3. 为什么放前端

| | 做法 | 判断 |
|---|---|---|
| **A（采用）** | 全前端筛选排序：数据集已在 `state.admin.users`，纯函数过滤 | 改一个字符立刻重画，零往返、零服务端改动 |
| B | 服务端加 `?status=&sort=&dir=&idleMin=` | 每敲一个字一次网络往返；要新增参数校验、边界用例、一整套服务端测试。当前规模（百级账号）**收益为负** |
| C | 超过 N 条自动切服务端 | 两套过滤逻辑必须永远保持语义一致，维护成本翻倍。YAGNI |

`/api/admin/overview` 本来就是「把全部账号给管理员」的接口，它没有分页，也不该有——
管理员视图的价值就在一眼看全。等账号真的上千条，再谈 B。

## 4. 筛选模型

一个对象，**唯一真源**：

```js
var adminFilter = {
    q: '',            // 搜索框：昵称 / 注册 IP / 最后登录 IP
    status: 'all',    // all | admin | suspect | dormant | nocourse | hascourse
    sort: 'regAt',    // regAt | lastLoginAt | loginCount | courseCount | idleDays | nickname
    dir: 'desc',      // asc | desc
    regFrom: '', regTo: '',                    // 注册时间区间（本地日）
    idleMin: '',                               // 至少 N 天没露面
    loginMin: '', loginMax: '',                // 登录次数区间
    courseMin: '', courseMax: ''               // 课表时段区间
};
```

`q` 现在只匹配 `nickname` 和 `regIp`（`app.js:712`），本设计**扩到 `lastLoginIp`**。
这是一处刻意的行为变化：输入框的提示语写的是「按昵称或 **IP** 筛一下」，
而管理员手里拿到的可疑 IP 往往来自登录记录而不是注册记录，只认一个 IP 会让人以为「搜不到就是没有」。
两个 IP 都认才符合提示语的字面意思。

**状态六选一**（互斥，不是叠加）：

| 值 | 含义 | 对应字段 |
|---|---|---|
| `all` | 全部 | — |
| `admin` | 管理员 | `u.admin` |
| `suspect` | 待复核 | `u.suspect` |
| `dormant` | 待清理 | `u.dormant` |
| `nocourse` | 未传课表 | `u.courseCount === 0` |
| `hascourse` | 已传课表 | `u.courseCount > 0` |

`dormant`（没传课表 **且** 30 天没露面）是 `nocourse` 的子集——两者都是有用的视图，
不合并：一个是「该清掉的」，一个是「还没开始用的」。

**默认排序 `regAt` + `desc`（最新注册在前）**，这是本设计唯一的**行为变化**（现在是注册升序）。
理由：管理页的高频场景是「刚才那批可疑注册是谁」，最新在前才用得上。
排序用 `Array.prototype.sort`（V8 稳定排序），并列时保持服务端原顺序。
昵称用 `localeCompare(b, 'zh')`。

- 排序方向按钮的**文字跟着方向变**（`↓ 降序` / `↑ 升序`），不靠图标猜
- 「更多筛选」的展开状态用 `hidden` 切换，不做动画（这里不值得）

## 6. 渲染与联动

`filterAdminUsers(users)` 一个纯函数，三处渲染共用：

```
q ──► status ──► regFrom/regTo ──► idleMin ──► loginMin/Max ──► courseMin/Max ──► sort
```

### 6.1 三张卡片一起跟着筛

按你的选择，**账号列表、待清理、异常注册**三处都跟随筛选；「群组」卡片不动。

**排序也作用于三处**，不只是账号列表。理由：这三张卡片都是「账号视图」，只是预设了不同的
子集条件。如果选「登录次数降序」之后，账号列表重排了而待清理卡片还是老顺序，
同一个页面上两套排序规则会让人无法预期。唯一被这一条改变的是「异常注册」——
它原来是固定的注册时间升序（`listSuspects()` 的 `createdAt` 升序），现在跟随所选排序。

### 6.2 「异常注册」卡片改从 `users[]` 派生

这是必要的一步，不只是顺手：现在这张卡片用的是 `a.suspects`，而 `store.listSuspects()`
（`store.js:687`）返回的是**精简副本**——只有 `nickname / regIp / createdAt / reason`，
**没有 `id`、没有 `idleDays`、没有 `courseCount`**。它根本没法参与筛选。

而 `users[]` 里本来就有 `suspect` + `suspectReason`，两者判定条件完全相同（都是 `u.suspect`）。
改成从 `a.users.filter(u => u.suspect)` 派生：

- 一套数据、一个筛选入口
- 卡片显示的信息不变（`regIp` / `suspectReason` / `regAt` 都在 users 里）
- 排列顺序不变（按 `regAt` 升序，和 `listSuspects()` 的 `createdAt` 升序一致）

`a.suspects` 仍然用于**概览的统计数字**（`stats.suspectCount` 由服务端算），只是不再用于渲染卡片。

### 6.3 概览数字**不**跟着筛

概览那六个格子（账号 / 管理员 / 已传课表 / 群组 / 待复核 / 待清理）**始终是全站全量**。
它是「这个站现在什么状况」，跟着筛选变会让这排数字失去意义。

筛选结果的数量放在**卡片标题旁边**：

- 无筛选：`83 个`
- 有筛选：`筛出 12 个 · 共 83 个`

### 6.4 被筛掉多少，要说出来

你选了「卡片一起跟着筛」，这是那个选择带来的**唯一真会踩的坑**：

> 筛选态下看到「待清理 0 个」，很容易读成「已经没有待清理的账号了」，
> 而真相是「当前筛选把它们挡住了」。

所以待清理 / 异常注册两张卡片在有筛选时，标题旁额外显示**「另有 N 个被当前筛选挡住」**。
账号卡片不需要（它有「共 X 个」做对照）。

### 6.5 `no-anim`

`renderAdminUsers` 现在用 `#admin-users` 上的 `no-anim` 抑制入场动画重播，条件是「有 q」。
放宽成「**任一筛选生效**」——否则点了状态胶囊，整个列表会重播一次入场动画，
每点一下闪一下。现有的回归测试（`screens.test.js:743`）仍然通过。

## 7. 四个必须写对的细节

### 7.1 注册时间按**本地日**解析

```js
// ✅ 当天 00:00（本地时区）
function dayStart(s) { var p = s.split('-'); return new Date(+p[0], +p[1] - 1, +p[2]).getTime(); }
// ❌ new Date('2026-09-15') 是 UTC 午夜
```

`new Date('2026-09-15')` 会被解析成 **UTC 午夜**。东八区下，9 月 15 日 00:00–08:00 注册的账号
时间戳小于这个值，**会被错误地排除在「9 月 15 日」之外**——正是最该被抓出来的那批深夜注册。
区间上界取 `dayStart(regTo) + 86400000 - 1`（当天最后一毫秒），保证**当天整天都算在内**。
这条要有专门的边界测试钉住。

### 7.2 `min > max` 自动交换

不做错误态、不弹提示。用户把 `30` 填进 min、`7` 填进 max，意思很清楚，就是「7 到 30」。
静默交换比多一个红色提示更省事，也不会让列表变成空的让人以为没数据。

### 7.3 空字符串 = 不限

数字输入框留空时 `.value` 是 `''`，`Number('')` 是 `0`——**必须显式判空**，否则「不限」
会被算成「等于 0」。用 `parseNum(v)` 返回 `null` 表示不限，别用 `|| 0` 或 `Number(v)`。

### 7.4 进页面重置

`openAdmin()` 现在会清空 `#admin-user-filter`（`app.js:592`）。筛选状态同样在进页面时重置成默认值。
理由：筛选是**临时的查看动作**，不是**配置**。下次进来看到一份被上次状态过滤过的列表，
却想不起来自己筛过什么，比每次都从头开始糟得多。

## 8. 测试（`test/screens.test.js`）

沿用那个自垫 DOM 的全量屏幕扫描（真实 `app.js` 原样跑起来）。垫片已经支持
`dispatch('change')`（`screens.test.js:1095` 有先例），所以 `<select>` 可测。

| 用例 | 断言 |
|---|---|
| 状态胶囊 | 点「管理员」只剩管理员；点「全部」恢复全量 |
| 排序 | 切到「登录次数」+ 降序，首位是登录最多的那个 |
| 更多筛选：天数 | `idleMin=30` 只留下 `idleDays >= 30` 的 |
| 更多筛选：区间 | 课表时段 1~2 个，边界值（正好 1、正好 2）必须在结果里 |
| **注册时间边界** | 选 `regFrom = regTo = 某天`，**当天注册的账号必须命中**（§7.1 的时区回归） |
| min > max | 自动交换，结果与正序填写一致（§7.2） |
| 卡片联动 | 筛「待复核」后，待清理/异常注册两张卡片同步缩小，并出现「被挡住 N 个」 |
| 概览不受影响 | 筛选前后 `#admin-stats` 的六个数字不变（§6.3） |
| 清空筛选 | 恢复全量，`no-anim` 摘掉 |
| 委托唯一 | `#admin-users` 上仍然只有 1 个 click 监听（延续 `screens.test.js:768` 那条重复绑定回归） |

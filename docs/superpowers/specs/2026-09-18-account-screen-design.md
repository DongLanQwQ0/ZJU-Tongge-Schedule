# 注销入口下沉到「账号」屏 —— 设计

> 一句话：**更多菜单里不再有注销，红色也不再出现在菜单里；账号的事收进一屏，顺带把「自己改密码」这个一直没有界面的功能补上。**

## 1. 现在的问题

`public/index.html` 的「更多」菜单（点顶栏 ⋯ 展开）一共 5 项：

```
🔗 分享给同学
🌙 切换深色 / 浅色
🛠 管理            （只有管理员看得到）
⎋ 退出登录          ← .danger，红
🗑 注销账号          ← .danger，红
```

「太明显」具体是三条：

1. **两个红色挨着**。菜单一共 5 项，红色占 2 项 —— 红色本该是稀缺信号，现在四成菜单是红的。
2. **它就贴在「退出登录」下面**，而退出登录是这个菜单里最常点的一项。手指落点差一行就是不可逆操作。
3. **🗑 图标把它抬成了「一级菜单项」**，和「分享给同学」平级。

**安全性不是问题，不用再加闸。** `deleteAccount()`（`app.js:1212`）已经是「先说清后果 → 再输密码」
两道提醒，误触根本删不掉。再加一层确认是拿仪式感掩盖层级没做好。这个设计只动**视觉层级**。

## 2. 改法

```
更多菜单（零红色）
├ 👤 账号          ← 新增，普通色，第一项
├ 🔗 分享给同学
├ 🌙 切换深色 / 浅色
├ 🛠 管理          （仅管理员）
└ ⎋ 退出登录       ← 去掉 .danger

账号屏（点 👤 账号 进来）
├ 昵称  张三        （只读）
├ 修改密码    ›     ← 新增，原来的 API 一直没有界面
├ ────────────────
└ 危险操作
   注销后账号、课表、备注都没了，无法恢复。
   [ 注销账号 ]      ← 小号红字按钮，不是整行大红块
```

### 2.1 为什么「退出登录」要去掉红色

退出是**可逆**的（重新登录就回来），注销是**不可逆**的。两个都用红色，等于告诉用户
「红的都没什么大不了」，真正危险的那个反而不突出了。红色留给不可逆的那一个。

### 2.2 为什么「账号」放第一项

它回答的是「我现在是谁、我的号能做什么」，是这一组里最像「入口」的一项；
放最后容易被当成和「退出」同类的收尾动作。

### 2.3 「退出登录」不搬进账号屏

它是高频动作，留在 ⋯ 菜单里保持一次点击。搬进账号屏会多一次点击，收益只是「结构整齐」，
不划算。（所以账号屏里不会再有第二个退出入口 —— 同一个动作不摆两处。）

### 2.4 账号屏里的注销为什么是小号红字

它不是这个屏的主角，用户是「来找注销」才看得到它。整行大红块在设置屏里仍然太吵；
小号红字按钮的强度刚好：找的时候一眼就有，不找的时候不抢戏。红色真正的高潮留在最后的
确认弹窗里（`.btn.armed`，第二下变红那一下）。

## 3. 改密码（顺带补上的窟窿）

`API.changePassword`（`public/api.js:134`）**定义了，但全项目没有任何地方调用它** ——
也就是说用户现在根本没法自己改密码，只能找管理员重置。账号屏正好给它一个家。

### 3.1 流程

一个弹窗三个框：**旧密码 / 新密码 / 确认新密码**。

客户端先拦（不发请求）：新密码至少 6 位、两次输入一致、新密码不能和旧密码相同。
服务端已有的校验（`validatePassword`）和限流（`pw:` 桶，错 3 次歇十分钟）照旧生效。

### 3.2 关键：改完之后这台设备会被踢下线

`store.setUserPassword()`（`shared/store.js:715`）最后一句是 `revokeUserSessions(id)` ——
**吊销这个用户的全部会话，包括当前这一条**。`test/server.test.js:670` 明确断言了这件事
（改完密码拿原令牌请求 `/api/me` 必须 401）。

所以前端必须处理，否则用户改完密码下一次点任何东西都突然回到登录页，像出了 bug。

**处理：用刚设的新密码静默重登一次。**

```
PUT /api/me/password 成功
  └─ POST /api/login（昵称 + 新密码）
       ├─ 成功 → 换上新令牌，人留在这台设备上，提示「其他设备上的登录都失效了」
       └─ 失败 → 清掉本地令牌，回登录页，提示「密码已改，请用新密码重新登录」
```

- **为什么不改服务端让它保留当前会话**：吊销全部是更有价值的性质 ——
  万一改密码的人是偷到令牌的，他改完就失去访问，不能再把新密码据为己有。
  为了省一次自动登录去削弱它不划算。
- **静默重登不引入新风险**：用户刚刚亲手证明了知道新密码，这一步没有多给任何人权限。
- 极端情况下重登会被要验证码（昵称连续登录失败过），所以必须有失败分支。

### 3.3 昵称为什么不能改

昵称是**全局唯一**的，而且被备注（`users[].remarks` 按 userId 索引）、群成员表、
审计日志按**昵称**记录的地方引用着（`appendAudit` 写的是昵称）。改它要动一串引用，
不是这次的事。账号屏**只读展示**昵称，并明说它不能改 —— 免得用户找不到入口以为是 bug。

## 6. 测试

| 用例 | 断言 |
|---|---|
| 菜单里没有注销 | `#more-menu` 里找不到 `#btn-delete-account`；菜单里**一个 `.danger` 都没有**（红色不再出现在菜单里） |
| 进得去账号屏 | 点 `#btn-account` → `activeScreen() === 'account'`，标题「账号」，昵称显示出来 |
| 注销搬过去了 | `#screen-account` 里有 `#btn-delete-account`；**两道提醒照旧**（点一下只有确认框，确认后才要密码） |
| 返回手势 | 从账号屏返回能回到首页，不会卡住 |
| 改密码成功 | 旧密码废、新密码能登；**这台设备没掉线**（紧接着 `/api/me` 还是 200）；提示里说明其他设备已失效 |
| 改密码：旧密码错 | 401，弹窗**不关**（让用户重填），红字提示 |
| 改密码：两次不一致 | 本地拦下，一个请求都不发 |
| 改密码：太短 | 本地拦下（< 6 位） |
| 监听只绑一次 | `#btn-change-password` 上只有一份 click 监听（这套测试里的老回归项） |

## 7. 已知限制

- **昵称改不了**（§3.3）。账号屏只读展示。
- **改密码会踢掉其他所有设备**，这是有意的（§3.2）。提示里会说明。
- 账号屏目前只有这三件事。将来的隐私设置、导出数据之类可以往这里放，但不预先搭架子。

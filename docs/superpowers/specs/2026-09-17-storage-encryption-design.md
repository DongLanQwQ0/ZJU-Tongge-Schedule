# 存储加密（最简方案）—— 设计

> 一句话：**一把根密钥，把姓名、备注、课表统一加密；钥匙不在数据卷里，所以文件被拿走也读不出。**

## 1. 目标与威胁模型

**只做一档防护**：

| 档 | 场景 | 结果 |
|---|---|---|
| **T1 文件被窃取** | 数据卷、备份、`dist/` 部署包、镜像层被拿走 | **全部敏感数据都读不出** ✓ |
| T2 拿到执行权限 | 攻击者能在服务器上跑命令（读得到 `process.env`） | **读得出**（明确接受） |

T2 挡不住是**信息论限制**，不是实现取舍：服务器必须能解密密文才能对外提供数据，所以运行时在用的钥匙对拿到执行权限的人必然可读。想连 T2 也挡，只有端到端加密（浏览器解密 + 群密钥分发），那是另一个量级的工程，不做（见 7.3）。

明确**不解决**的：在线越权读别人的数据（授权问题）、磁盘物理加密（宿主机层面，LUKS / 云盘加密）。

**T1 的前提**：根密钥不在被拿走的那份东西里。见第 7 节。

## 2. 加密范围

| 数据 | 存放位置 | 加密 |
|---|---|---|
| 昵称 | `users.json[uid].nickname` | ✅ |
| 课表 | `users.json[uid].courses` | ✅ |
| 私密备注（我给同学起的真名） | `users.json[uid].remarks` | ✅ |
| 对外备注（我在群里显示的名字） | `groups/<code>.json.selfRemarks[uid]` | ✅ |

**保持明文**：时间戳、`pwSalt`/`pwHash`（哈希本身不可逆）、群成员 `userId` 列表、邀请码。

课表加密后主路径不用改：撞课比对在浏览器里算（`public/app.js` 调 `shared/compare.js`），服务端只负责"读文件时解密、写文件时加密"，内存里和今天一样是明文。

## 3. 一把钥匙

```
═══════════ 部署时（一次性） ══════════════════════════════════════════════

   随机 32 字节
      └──► TONGGE_ROOT_KEY ──写入──► /etc/tongge/key.env
                                      （部署目录之外：不进数据卷、不进备份、不进镜像）
                                      └── 服务启动读入 ──►  K_root ★ 内存

═══════════ 运行时 ═════════════════════════════════════════════════════════

                          K_root ★
        ┌───────────────────┬───────────────────┬──────────────────┐
        │ AAD: nickname     │ AAD: course        │ AAD: remarks     │ AAD: selfremark
        ▼                   ▼                    ▼                  ▼
    昵称密文            课表密文            私密备注密文        对外备注密文
   users.json          users.json          users.json       groups/<码>.json

   ┌────────────────────────────────────────────────────────────┐
   │ 落盘的全部内容：只有密文 + 密码哈希 + 盐 + 非机密元数据      │
   │ —— 没有任何一把明文钥匙                                     │
   └────────────────────────────────────────────────────────────┘
```

- `K_root`：32 字节随机，来自环境变量 `TONGGE_ROOT_KEY`，**唯一的一把钥匙**
- 加密算法：`AES-256-GCM`，每次随机 12 字节 IV
- **域分离靠 AAD，不派生多把钥匙**（见第 4 节）。将来真需要"某一类单独轮换"再把 `HKDF(K_root, info=类别)` 引进来，现在不做
- 随机 IV 的碰撞门槛是"同一把钥匙下加密十亿条消息"级别，本项目远够不上

**为什么这版不需要恢复流程**：密钥只来自环境，**跟任何人的密码都无关**。所以用户忘记密码、管理员重置密码、超管改自己的密码，**都不影响任何数据**——备注不会丢，也就不需要 DEK、escrow、过渡桥那一整套。（那一套的唯一收益是"备注在 T2 档也读不出"，而 T2 已经明确不设防，所以不划算。）

## 4. 数据格式

所有密文用同一个形状（`AES-256-GCM`，12 字节 IV，16 字节 tag，Base64）：

```jsonc
{ "v": 1, "iv": "...", "ct": "...", "tag": "..." }
```

**AAD 绑上下文**（域分离靠它，不靠命名约定）：

| 用途 | AAD |
|---|---|
| 昵称 | `tongge:v1:nickname:<uid>` |
| 课表 | `tongge:v1:course:<uid>` |
| 私密备注 | `tongge:v1:remarks:<uid>` |
| 对外备注 | `tongge:v1:selfremark:<groupCode>:<uid>` |

把 A 的密文挪到 B 名下、把课表冒充备注、把甲群的对外备注挪到乙群——**都会解密失败**，而不是悄悄生效。

```jsonc
// users.json 的某个用户（其余字段不动）
{
  "id": "u_69753a87",
  "nickname": { "v": 1, "iv": "...", "ct": "...", "tag": "..." },
  "courses":  { "v": 1, "iv": "...", "ct": "...", "tag": "..." },  // 内容是课表数组的 JSON 串
  "remarks":  { "v": 1, "iv": "...", "ct": "...", "tag": "..." },  // 内容是 {他人id: 备注} 的 JSON 串
  "pwSalt": "…", "pwHash": "…"
}
```

`v` 是格式版本，将来换算法或轮换根密钥时靠它做**惰性重写**（读到旧版本顺手升级），不必停机批处理。

## 5. 读写路径

加解密**只发生在文件读写边界**（`readJson` / `writeCritical`）：读文件时把四个字段解成明文放进内存（和今天完全一样），写文件时再加密。

所以：路由、撞课比对、ICS 导出、前端渲染、管理页统计、**绝大部分现有测试都不用动**。没有"解锁时机"、没有会话密钥、没有内存密钥缓存——`K_root` 常驻内存就够了。

## 6. 超管模型

**唯一超级管理员**，与普通管理员解耦：

- `users.json[uid].super = true`，**全局只允许一个**；由迁移参数写入（`--migrate-vault --super <昵称>`），启动自检发现数量 ≠ 1 就在横幅上告警
- 普通管理员 `admin = true`：管群、管用户、重置普通用户的登录密码，**碰不到超管**
- 只有 `super` 能访问敏感原文（6.2），每次写审计

### 6.1 守卫清单

| 守卫 | 现状 → 目标 |
|---|---|
| 不能撤销自己的超管权限 | 用户明确要求；**并且任何人都不能撤销 `super`**（含超管自己） |
| 不能删除超管 | 现在只挡了"删自己"——**普通管理员可以直接删掉超管**，必须堵 |
| 普通管理员不能重置超管的密码 | 现在**完全没有守卫**——等于普通管理员可接管超管账号，必须堵 |
| 不能授予第二个 `super` | 授 `super` 只能走服务器 CLI（`--set-super <昵称>`，需二次确认） |
| 普通管理员之间互相授/撤 | 照旧，保留现有"你是唯一管理员时先授权再撤自己"的守卫 |

> 注：这版不再需要"禁止超管自己重置密码"那条。上一版需要它，是因为 escrow 钥匙由超管密码派生，换成随机临时密码会让全站备注失联；现在密钥来自环境，**超管怎么改密码都不影响数据**。

### 6.2 超管访问敏感原文

"可以通过超管账号访问"落到一个显式接口上：

`GET /api/admin/users/:id/notes`（**仅 `super`**，否则 403）→ 返回该用户的私密备注明文 + 写审计 `notes_view`（by / target / ip）

理由：服务器本来就有能力解密（6 节前提），隐藏它只会让人以为"谁也看不到"；**显式化 + 审计**才是诚实的做法。界面入口可以后置（先只做接口）。普通管理员没有这个接口，也就拿不到别人的备注。

## 7. 已知缺口与不做的事

### 7.1 T2 档：拿到执行权限就全读得出

`process.env` 里就有根密钥，能读它就能解开全部四类数据。**这是本设计明确接受的**（见第 1 节）。

### 7.2 根密钥和数据一起被拿走

例如密钥文件就躺在部署目录里、又被一起备份 —— 同样全部可解。**密钥必须和数据分开存放**，这是 T1 有效性的全部基础。

### 7.3 明确不做

- **端到端加密**（T2 也读不出）：需要浏览器端派生、群密钥分发与成员变动轮换、登录协议改造。工作量大一个量级
- **按用户密码派生 + 超管 escrow 恢复**（上一版的方案）：唯一收益是"私密备注在 T2 档也读不出"，代价是 DEK、三份包装、过渡桥、恢复接口、超管密码轮换全量重包。在 T2 不设防的前提下不划算
- **密码不裸传**（浏览器 PBKDF2 派生 `authKey`）：能改善信任模型，但属于独立子系统，单独出设计
- **在 HTTPS 之上再套一层前端固定密钥**：密钥在前端可见，是安全剧场

## 8. 密钥保管与运维

- `TONGGE_ROOT_KEY`：32 字节随机（64 hex）。服务器上一般没装 node（应用跑在容器里），
  所以用容器生成：
  `docker run --rm node:22-alpine node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`
- **放在部署目录之外**（例如 `/etc/tongge/key.env`），compose 用 `env_file` 引用；**不进数据卷、不进镜像、不跟数据一起备份、不进版本库**
- **缺失就拒绝启动**并打印生成命令——绝不允许悄悄退回"无加密"模式
- **启动自检（fail-fast）**：拿根密钥试解一条已有密文（例如任一昵称）。解不开说明密钥不对或数据被换过——**立刻拒绝启动**，而不是带着错密钥跑起来把后续写入的数据一起弄坏
- **根密钥必须和备份一起保管**：它丢了不是"读不出数据"这么轻——**连登录都做不了**（按昵称查账号要先解密昵称）
- 备份要加密；迁移产生的 `.plaintext-<ts>` 在确认备份可用后**必须删除**（它是新的泄漏点）

## 9. 配套改动（同一批做，都属于"读盘即得"这一类）

1. **会话令牌哈希化**：`sessions.json` 现在以**明文令牌为键**——拿走文件的人可以直接调接口冒充任意用户，服务端还会替他解密姓名。文件加密再严，不堵这条等于没做。改为存 `sha256(token)`；存量迁移时把现有键就地换成哈希（用户浏览器里的令牌照旧有效，不用重新登录）
2. **部署产物不带数据**：`.dockerignore` 排除 `data/`，Dockerfile 不再 `COPY data/`，`INCLUDE_SESSIONS` 默认 `false`；`dist/` 打包脚本排除 `data/`。首次部署用显式导入，不把数据烧进镜像
3. **传输层**（反代侧，一行配置的事）：强制 HTTPS 跳转 + HSTS；应用侧 CSP 加 `upgrade-insecure-requests`

## 10. 失败模式

| 场景 | 结果 |
|---|---|
| 数据卷被拿走，根密钥安全 | 姓名、两类备注、课表**全部读不出** ✓ |
| 数据卷 + 根密钥都被拿走 | 全部可解（7.2） |
| 拿到执行权限（T2） | 全部可读（7.1） |
| 只有根密钥泄漏、数据卷安全 | 无影响（数据没被拿走） |
| **根密钥丢失（且无备份）** | **无法登录**（昵称解不开就查不到账号）→ 必须和备份一起保管 |
| 根密钥被换错 | 启动自检失败、拒绝启动（不会写坏数据） |
| **用户忘记密码** | **什么都不影响**：重置后照常读写课表与备注（密钥与密码无关） |
| 超管忘记密码 | 与加密无关（不参与密钥）；仅影响 6.2 的访问能力 |

## 11. 测试要点

- **vault**：seal/open 往返；**AAD 跨用户、跨群、跨用途必须失败**；错误钥匙失败；篡改 `ct`/`tag` 失败；版本号字段存在
- **store**：四个字段读回仍是明文；写盘后文件里搜不到任何明文姓名；迁移**幂等**（重复执行不重复加密）；回滚可用
- **流程**：注册后课表与备注可读；改密码、管理员重置密码后**数据照常可读**（这条是本方案相对上一版最大的行为差异，必须有测试守住）
- **守卫**：不能撤销 `super`（含自己）、不能删 `super`、普通管理员不能重置 `super` 密码、不能授予第二个 `super`；`GET /api/admin/users/:id/notes` 非 super 返回 403 且不留明文
- **fail-fast**：用错根密钥启动必须失败
- **回归**：现有用例注入固定 `TONGGE_ROOT_KEY`（测试里用固定值，**绝不使用任何真实口令**）

## 12. 交付步骤（三步，每步可独立验证）

1. `shared/vault.js` + 单测 —— 纯新增，不动现有行为
2. store 读写边界接入（昵称 / 课表 / 私密备注 / 对外备注）+ 迁移命令 + 现有测试适配 —— **此步之后，文件里再无明文姓名与课表**
3. 超管模型（`super` 唯一 + 守卫清单 + 备注访问接口与审计）+ 配套：会话令牌哈希化、镜像/部署包不带 `data/`、部署与密钥保管文档

## 13. 部署与迁移顺序

这套服务的部署方式是**手动用仓库代码覆盖**（`git pull` 到部署目录），所以顺序必须写死。三条约束：

1. **迁移必须由新代码执行**——旧代码不认识密文格式。所以代码要先就位。
   注意区分两件事：迁移是"新代码在运行"（CLI 模式，不启 HTTP），但**必须在旧服务停掉之后**跑。
2. **迁移期间服务必须停**——运行中的服务内存里是明文，任何一次写入都会把迁移结果覆盖回明文。
3. **服务启动时检测到未迁移的明文就拒绝启动**，并提示跑迁移命令。避免"一半明文一半密文"的中间态悄悄上线。

```bash
# 0. 备份（数据在命名卷 tongge-data 里）
docker run --rm -v tongge-data:/data -v "$PWD:/backup" alpine \
  tar czf /backup/tongge-$(date +%Y%m%d-%H%M).tar.gz -C /data .

# 1. 生成根密钥，放到部署目录之外 —— 绝不能和数据放一起、也绝不能进备份
# 服务器上一般没装 node（应用跑在容器里），所以用容器生成一把
KEY=$(docker run --rm node:22-alpine node -e "console.log(require('crypto').randomBytes(32).toString('hex'))")
sudo install -d -m 700 /etc/tongge
printf 'TONGGE_ROOT_KEY=%s\n' "$KEY" | sudo tee /etc/tongge/key.env >/dev/null
sudo chmod 600 /etc/tongge/key.env

# 2. 代码就位（覆盖）
cd /opt/tongge && git pull
#    compose 的 tongge 服务下加一行：env_file: /etc/tongge/key.env

# 3. 停掉旧服务（这一步不能省：不停会覆盖迁移结果）
docker compose stop

# 4. 用新代码跑迁移（CLI 模式，不启 HTTP；缺根密钥会直接报错并告诉你怎么生成）
docker compose run --rm tongge node server.js --migrate-vault --super DongLan

# 5. 起服务
docker compose up -d --build

# 6. 验证：能登录、能看备注；再抽查卷里搜不到任何备注原文
docker run --rm -v tongge-data:/data alpine \
  grep -rl "把这里换成你知道的某条备注原文" /data || echo "文件里已无该明文 ✓"

# 7. 确认备份可用后，删掉迁移留下的明文副本（它本身也是泄漏点）
docker run --rm -v tongge-data:/data alpine sh -c 'rm -f /data/*.plaintext-*'
```

**为什么不做"读到明文就顺手加密"的惰性迁移**：那样没被碰过的字段会一直是明文，"文件被拿走读不出"这个目标就兑现不了；而且一半明文一半密文的中间态最难排查。宁可停机几分钟、跑一条命令、看一眼结果。

# 群码不再当门票，默认给一条永久链接 —— 设计

> 一句话：**群码退回成「群的地址」，入群只认邀请链接；每个群默认带一条永久链接；
> 群主把链接都收光之后，成员看到的是「群主似乎没有分享他的群群~」，而不是一张坏掉的卡片。**

## 1. 起因：一张坏掉的卡片

群里**没有还能用的邀请链接**时，成员打开群组页看到的是：

```
把邀请码或二维码发给同学
        ——                    ← 占位符，不是码
  ┌──────────────────┐
  │ 没有可用的邀请链接 │        ← 本该是二维码的地方，摆了个白底提示
  └──────────────────┘
 [复制邀请码] [复制链接] [放大二维码]   ← 三颗全灰
现在没有能用的邀请链接了。
```

同一张卡片上，群主看到的是**正常的**（会退回他自己的永久码）。也就是说这是一个
「群主看不见、成员天天见」的状态。

只读探针跑了一遍本机数据：**5 个群里有 4 个**是上面这个样子（1 个从没发过票、
1 个票全过期、1 个票全作废）。所以这不是边角情况 —— 只要群主没手动点过「生成」，
全体成员看到的就是这张坏卡片。用户的原话：

> 手动创建新邀请链接就不会了 …… 但这不应该修一修吗

根因是两条，第二条比第一条更值得修：

1. `currentDisplayCode()`（`public/app.js`）只在**群主**身上回落到永久码，
   成员没有兜底 → 返回 `null` → 渲染成上面那个「——」+ 空二维码 + 三颗灰按钮。
2. **同一件事有两个说法。** 首页那张群卡片（`public/app.js:1202`）把**群码**当邀请码
   印给成员看（`邀请码 80607908 · 7 人`），进了群组页却说「没有能用的邀请链接」。
   那个「成员分享」开关一边决定「看不看得到」，界面一边给一边藏。

## 2. 为什么会这样：群码身兼两职

`shared/store.js:950` 那段注释把设计意图写得很清楚：

> `g.code` —— 群的**永久地址**，也是文件名。永远有效，永远不变。
> 群主自己用它是为了「回到自己的群」，**不当作对外分享的凭证**。

但实现是反的：

| 位置 | 现状 |
|---|---|
| `joinByInvite()`（`store.js:1267`） | 认完票之后**还认群码**，注释说「改版前发出去的链接用的就是它，不能让它失效」 |
| `groupDetail()`（`store.js:1587`） | 把 `g.code` 当 `ownerCode` 发给群主，于是界面把它当票用 |
| `createGroup()`（`store.js:921`） | 新群**一枚票都没有** —— 「群里没有票」是新群的默认状态 |
| `public/app.js:1206` | 首页卡片把 `g.code` 印成「邀请码」 |

合起来：**群码是一张不可收回、不可过期的永久门票**。谁拿到都能进，群主想收回
只能「换群码」——而换群码会改掉群的地址本身。

上一份设计（`2026-09-18-member-share-toggle-design.md`）的 §7 已经写明这条限制，
并且列了「把群标识和邀请码拆开」的代价，结论是**这次不做**：

> 换来的只是「成员多走一步 devtools」。哪天真要把它当安全边界用，再单独评审这一条。

**这次做**，但动机不是安全 —— 是那张卡片，以及「同一个东西两个说法」。
附带的好处：拆开之后，成员分享开关第一次成为**真边界**（§7 第一条限制消失）。

## 3. 决定

### 3.1 群码只作地址，不再能入群

`joinByInvite()` 删掉「回落群码」那一段。`g.code` 仍然是：群文件名、
`/api/groups/:code/*` 的路径参数、前端 `state.group.code`。

它照旧出现在每个成员都拿得到的响应里（前端要拿它寻址），但**它不再是一张票**，
所以「泄漏」它没有后果 —— 这条正是「成员分享」能变成真边界的原因。

### 3.2 每个群默认带一条永久链接

- 建群时（`createGroup`）就带上：`ttl: 'never'`、备注「默认链接」。
- 老群由 `init()` 一次性补齐（§4.2）。
- 为什么必须有它：**它是一条可以单独收回、可以随时重发的票**，群码做不到。
  而且有了它，「成员能不能分享」才有个东西可分享 —— 否则成员分享开关开着，
  成员手上却什么都没有，就是这次要修的那个矛盾。

### 3.3 「补过一次」要记成事实：`invitesSeeded`

群主**故意**把票收光之后，成员该看到 §6.2 那句文案，而不是我们下次启动时
又偷偷补一枚回去。所以不能用「`invites` 是空的就补」来判断 —— 判不出
「老群还没补过」和「群主刚删光」的区别。

用标记：`g.invitesSeeded === true` 表示这个群已经过了这一步。

| 群的状态 | `init()` 怎么做 |
|---|---|
| 没有 `invitesSeeded`、一枚票都没有（老群） | 补一枚永久票 + 打标记 |
| 没有 `invitesSeeded`、但有票（老群，用过这个功能） | 只打标记，**不动票** |
| 有 `invitesSeeded`（新群，或群主删光过） | 什么都不做 —— 这是「群主似乎没有分享他的群群~」的来源 |

### 3.4 删掉「换群码」

群码不再是凭证之后，「换群码」不再收回任何东西，却会改掉群的地址
（前端手上那个 `code` 立刻全部 404）。它从一个安全动作退化成一个危险动作，
所以连存储函数、两条路由、前端按钮一起删（§4.5、§5、§6.5）。

`resolveGroupFile()` 里对 `codeRotatedFrom*` 的兼容读**保留**：老数据里确实有换过码的群，
删了就读不回来了。只是不再产生新数据。

### 3.5 邀请码全局唯一

票价现在是唯一的入口，而 `addInvite()` 只在**本群内**查重（`store.js:1163`）。
两个群各持一枚同码的活跃票时，`joinByInvite()` 按目录顺序先撞上谁就是谁 ——
**静默进错群**，而且从现象上根本看不出原因。

改成：生成时扫一遍所有群文件，把「所有群的 `code` + 所有历史票码」当已用集合。
`newGroupCode()` 是 10⁸ 空间、每群上限 20 枚，撞的概率本来就极低，
但这个错误的代价（进错群 + 难查）远大于一次目录扫描，所以买这个确定性。

注意查重范围是**全部历史**（含作废/过期）：作废码被重新发出来，
等于让拿到旧链接的人莫名其妙重新获得入口 —— 这是这个功能最不该出的错。

## 4. 存储层（`shared/store.js`）

| 函数 | 改动 |
|---|---|
| `createGroup()` | 建群时写一枚默认票（永久、备注「默认链接」）+ `invitesSeeded: true` |
| `init()` | 新增 `seedLegacyInvites()`：按 §3.3 的表补齐老群；有改动的才写盘，启动时打一行日志 |
| `joinByInvite()` | 删掉「回落群码」那段（`1267-1274`）；`readdir` 结果排序，保证命中确定 |
| `addInvite()` | 生成前收集全局已用码（`usedCodes()`），撞了就换 |
| `revokeInvite({issueNew})` | 同上（这条路也会造票） |
| `groupDetail()` | **去掉 `ownerCode`** —— 没有「群主自己的永久码」这个概念了 |
| `listGroupsForUser()` | 加 `shareCode`（见下表）；`code` 保持是群码 |
| `rotateGroupCode()`、`codeBelongsTo()` | 删。`codeBelongsTo()` 本来就是死代码（全仓库只有定义，没有调用） |

`shareCode` 决定首页卡片印什么：

| 看的人 | `shareCode` |
|---|---|
| 群主 | 最新一枚**还能用**的票的码 |
| 成员，且 `memberShare` 开着 | 同上（成员能转发的东西跟群主一样） |
| 成员，但 `memberShare` 被关掉 | `null`（首页不印码，与群组页一致） |
| 还没通过审批的申请人 | `null`（还没进群，谈不上分享） |
| 一枚能用的票都没有 | `null` |

## 5. 服务端（`server.js`）

删两条路由：

| 路由 | 行 |
|---|---|
| `POST /api/groups/:code/rotate-code` | 818 |
| `POST /api/admin/groups/:code/rotate-code` | 1055 |

`server.js` 的路由总数 **34 → 32**。
`test/admin.test.js` 里那份手工维护的 26 条清单本来就没含换码路由（它数的是
「每个功能面各一条」，不是总数），所以那条审计不用改。
`group_rotate_code` / `admin_rotate_group_code` 这两个审计事件名从来就不在
前端 `AUDIT_LABEL` 里（老日志里它们本来就显示成英文原名），所以那边也不用动。

`/api/groups/:code/join` 的注释要改：它现在只认邀请链接（`joinByInvite` 内部已保证）。

### 6.5 管理页去掉「群自己的码」

## 7. 代价（这一节是重点）

- **已经发出去的「群码链接」全部失效。** 群里已有的成员不受影响（成员按 userId 记，
  和票无关），但任何人手里那条 `?code=<群码>` 链接从此进不来。
  这正是这次要做的事（那条链接不可收回），代价就是它一次性全部报废 ——
  **群主需要重新发一次新链接**，老群补齐的那枚默认票就是新链接。
- 首页卡片上那行「邀请码」以前印的是群码，现在印的是票；群主如果一直靠复制群码
  拉人，会发现码变了。这是设计目的，不是 bug。
- **不可逆**：`invitesSeeded` 打上之后，删光票的群不会被自动补回（§3.3 是有意的）。
- **memberShare 从此是真边界**：成员再也读不到任何能用的码，也不再能靠「读响应」绕过。
  v8 留下的那个「假开关」问题到这里才算关掉。
- 老数据里的 `codeRotatedFrom` / `codeRotatedAt` 字段保留但不再产生新值。
- **没有通知**：群主收光链接之后，成员要重新进群组页（或刷新首页）才看得到变化 ——
  这个应用没有服务端推送。

## 9. 线上迁移（这一节是重点）

线上跑的是旧版本，数据是旧形状，用户浏览器里存着旧前端。逐条交代清楚。

### 9.1 「换群码」删了，线上那些 6 位老码怎么办

这是删掉换群码之后最该问的问题，先回答：**不用管，它们已经自动无害了。**

换群码当初存在的理由写在它的旧注释里：「改版前那批 6 位老码，10⁶ 空间配 20 次/分钟的
限流，枚举完只要一个多月」。注意它防的是**枚举入群** —— 而这次改动之后
**群码根本不能入群**（§3.1），枚举一个不能当门票的地址没有任何收益。

实测本机这份线上形状的数据（5 个群、8 枚票）：

| 实测项 | 结果 |
|---|---|
| 6 位码出现在哪 | 只在**群码**上（3 个老群），票码一个 6 位都没有 |
| 票码长度 | 全部 8 位 —— 票是这个功能上线后才有的，`newGroupCode()` 一直产 8 位 |
| 换过码的群（`g.code` ≠ 文件名） | 0 个；但代码路径已实测（§9.2） |

所以：**没有「6 位票」需要淘汰**，删掉换群码不留缺口。真出现 6 位票（理论上只可能来自
手改数据），群主在管理页单独作废那一枚即可 —— 那本来就是这个功能该有的粒度。

### 9.2 「换过码」的群（老数据里 `g.code` ≠ 文件名）

这类群的兼容读**必须**留着（`resolveGroupFile` 的 `codeRotatedFrom*` 判断），
因为文件名是内部存储键、`g.code` 才是地址，删了就读不回这些群。

新加的「补默认票」全程按**文件名**写盘（`path.join(GROUPS, f)`），不经过 `groupFile(code)`，
所以对这类群同样成立。临时目录里造了一个换过码的群实测：

```
补齐后：文件=82133161.json  code=99998888  票数=1  seeded=true
readGroup(新码)     -> ok
readGroup(老码)     -> null（对的：换掉的码不该再解析成地址）
addInvite(新码)     -> 落进同一个文件 ✓
用票入群            -> ok
```

### 9.3 迁移会写什么、写多少、可不可逆

**第一次用新版本打开数据目录就是一次迁移**，而且是**写操作**：

| 写什么 | 哪些文件 | 说明 |
|---|---|---|
| 加一枚永久票 `invites[]` | 一枚票都没有的老群 | 群主从此有东西可分享 |
| 加 `invitesSeeded: true` | **所有**还没打过标记的群 | 记录「这一步做过了」 |

三个必须知道的性质：

1. **它是幂等的**：打过标记的群不再动（`init()` 跑一百次结果一样）。
2. **它不碰 `updatedAt`**：这不是用户做的事，改了会让首页排序与 180 天清理的口径漂移。
3. **它发生在 `init()` 里，所以任何入口都会触发** —— 起服务、`--make-admin` 这类 CLI、
   甚至「只想看一眼数据」的临时脚本。我自己写探针时就撞上了：脚本注释写着「只读」，
   第一行输出却是 `已给 3 个老群补了默认链接`。**别拿 `init()` 当只读工具用**；
   真要只看不写，直接读 JSON（线上是密文，那就得接受看不出内容）。

因此**运维顺序必须是：先备份 `data/`，再跑新版本**。反过来的话，备份里已经是迁移后的状态，
「回滚到迁移前」就没有干净的落点了。

### 9.4 旧链接（`?code=<群码>`）全部失效

这是 §7 那条代价在线上的一次性账单，写法要具体：

- **谁能感知**：只有**还没进群的人**。已经进群的人按 `userId` 记，完全不受影响。
- **哪条链接死了**：群主以前那条「自己的永久码」链接 —— 那曾经是**最主要的分享路径**
  （首页卡片印它、群组页展示它、二维码也是它）。它现在会 404。
- **群主该做什么**：把新的默认链接重新发一次。老群补齐的那枚票就是新链接，
  群组页上直接显示，复制即用。
- **要不要做「一键群发」**：不做。应用没有推送，也没有用户的联系方式，
  唯一的渠道是群主自己那个微信群 —— 那本来就是他发链接的地方。

### 9.5 老前端 + 新服务端：为什么**故意**不给 `ownerCode` 兜底

部署后总有一段时间，用户浏览器里是**旧缓存的前端**。旧前端的 `currentDisplayCode()`
在群主身上会回落到 `g.ownerCode`；新服务端不再下发这个字段。于是旧前端的群组页会显示
那张「——」+ 空二维码 + 三颗灰按钮的坏卡片 —— **正是这次要修的东西**。

要不要为了平滑过渡，临时继续下发 `ownerCode`？**不要**，两个选项不对等：

| 做法 | 旧前端看到什么 | 后果 |
|---|---|---|
| 继续下发 `ownerCode` | 一切照旧，群主看到自己那个群码，能复制 | 他复制出去的是**已经进不了群的死链接**，而且看不出来 |
| 不发（本次选择） | 一张明显坏掉的卡片 | 用户会去刷新 —— 刷新就拿到了新前端 |

**坏卡片是自愈的，死链接不是。** 另外 `/app.js` 是 `no-cache`（每次回源，
只有 `/lib/`、`/img/mascot/` 长缓存），所以一次刷新就能拿到新前端；
已经开着不刷新的标签页会一直停在旧版，这没法避免，也不值得为它把兼容层留在服务端。

### 9.6 回滚

| 方向 | 结论 |
|---|---|
| 新数据 + 旧版本 | **安全**。多出来的 `invites` / `invitesSeeded` 对旧代码是惰性字段：旧 `invitesOf()` 认已有的数组，旧前端照旧能跑 |
| 回滚之后老链接会不会复活 | **会**。旧版本仍然把群码当票，所以滚回去等于把这层安全改动撤掉。这是「回滚」的定义，不是 bug —— 但要写在这里，免得有人以为回滚只是换回界面 |
| 已经发出去的新票 | 旧版本也认（`invites[]` 是旧功能），所以回滚不会打断正在流通的新链接 |

### 9.7 会消失的接口

`POST /api/groups/:code/rotate-code` 与 `POST /api/admin/groups/:code/rotate-code`
部署后返回 404。管理页从来没有这两颗按钮（只有群组页的邀请管理页有），
所以正常用户无感；如果有运维脚本或书签指着它，会在这里断掉。

### 9.8 运维清单

1. `data/` 全量备份（**迁移前**，见 §9.3）
2. 跑存储加密迁移命令（老流程，与本改动无关，但 `init()` 会写盘，所以必须先完成）
3. 停服 → 换新版本 → 启动
4. 看启动日志：`[store] 已给 N 个老群补了默认链接（群码从今天起不能入群）`。
   N = 0 也正常（说明每个群都自带票了，或者都是老群但已有票）
5. 通知群主：**把新的分享链接重新发一次**（§9.4）
6. 手机 / 电脑各刷新一次页面（§9.5）
